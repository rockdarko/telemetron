<objective>
Patch `roles/garage/tasks/bootstrap.yml` to make Garage S3 key creation idempotent against preserved metadata volumes. The current bootstrap creates a new `telemetron` key whenever the host-side credentials file (`{{ garage_s3_credentials_file }}`) is absent, without checking whether a key with that name already exists in Garage's preserved metadata. When `roles/garage/tasks/uninstall.yml` (Phase 10) removes the credentials file as designed but the `telemetron_garage_meta` volume is preserved (also as designed by D-141), the next `playbooks/deploy_docker.yml` run produces TWO keys named `telemetron` in Garage metadata. The downstream `bucket allow --key telemetron` command (step 9) filters by name and fails with `GetKeyInfo InvalidRequest (400): Bad request: 2 matching keys` on all 5 telemetron buckets (loki-chunks, tempo-traces, mimir-blocks, mimir-ruler, mimir-alerts).

Purpose: Close 11-VERIFICATION.md gap G-01 (orphan Garage S3 key on conservative undeploy + redeploy) and transitively unblock 11-HUMAN-UAT.md scenario 4b (G-02 -- same code path as scenario 1, skipped during UAT for that reason). The fix is a cross-phase patch: Phase 11's UAT surfaced the defect; the bug lives in Phase 8's `roles/garage/tasks/bootstrap.yml`; the artifact (this plan + the resulting commit) lands in Phase 11's directory by operator decision (keep all M1.2 undeploy / recovery work bundled in v1.2.0 milestone). Phase 10's `roles/garage/tasks/uninstall.yml` is NOT touched per D-141 trust -- option A from 11-HUMAN-UAT.md G-01 recommended-fix is the chosen approach.

Output: One modified file -- `roles/garage/tasks/bootstrap.yml` -- with three new branches inserted between existing step 7c (set credential facts from host file) and existing step 7d (create new key):

1. **Discovery step** -- query existing keys matching `{{ garage_s3_key_name }}` in Garage metadata; register `garage_existing_telemetron_keys` fact (list of key IDs).
2. **Recovery branch** (exactly one existing key + no host file) -- extract the existing key's secret via `garage key info --show-secret`; populate the same `garage_s3_access_key_id` + `garage_s3_secret_key` facts that the first-run branch sets; persist to `{{ garage_s3_credentials_file }}` (mode 0600) so the NEXT run's step 7a host-file check hits the fast path.
3. **Orphan-failure branch** (two or more existing keys) -- fail loudly with `ansible.builtin.fail` whose message contains `orphan key cleanup needed` and the verbatim operator workaround command.

The existing first-run branch (steps 7d / 7e / 7f) is gated on the zero-existing-keys condition so the three branches are mutually exclusive.
