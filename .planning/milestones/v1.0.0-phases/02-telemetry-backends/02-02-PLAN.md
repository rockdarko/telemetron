<objective>
Port the Tempo role from the upstream INSPQ stack into `roles/tempo/`, configured for Tempo 2.10.5 monolithic mode (`-target=all`) against the MinIO `tempo-traces` bucket bootstrapped in Phase 1. Wire the role into `playbooks/deploy_docker.yml` after `loki` (per D-23) so the playbook stays runnable at every commit (minio → loki → tempo).

This plan mirrors the Phase-1 canonical `roles/minio/` template AND the just-landed Plan 02-01 `roles/loki/` shape. The Tempo-specific work is dense:
1. **D-29 / BACK-05 alt OTLP ports** — receivers bind to `:14317`/`:14318` (internal-only on the telemetron bridge), leaving the standard `:4317`/`:4318` free for the Phase 3 OTel Collector.
2. **D-34 dual-knob retention (Pitfall 10)** — both `block_retention: 168h` AND `compacted_block_retention: 1h` MUST be set. Single-knob retention silently fails (the highest-impact M1 Tempo pitfall).
3. **D-38 metrics-generator path (b)** — enable processor-only operation (`service-graphs`, `span-metrics`, `local-blocks`) with `metrics_generator.storage.path` for the local WAL; intentionally NO `remote_write` block (no cross-backend startup dependency on Mimir). Resolved by RESEARCH Finding 1.
4. **D-28 gRPC port pin** — explicit `server.grpc_listen_port: 9096` (default 9095 would clash with Loki on a single host).
5. **D-39 S3 endpoint format gotcha** — Tempo uses `endpoint: minio:9000` (no `http://` prefix; `insecure: true` handles HTTP), unlike Loki which includes the scheme.
6. **Healthcheck under distroless (RESEARCH Finding 6)** — Tempo 2.10.5 is distroless with no shell. The native `-health` binary may or may not be present in this tag (RESEARCH MEDIUM confidence). Task 2 includes a healthcheck-probe step that runs `docker run --rm grafana/tempo:2.10.5 -help 2>&1 | grep -i health` at execute time and selects between (a) Docker HEALTHCHECK with `CMD ["/tempo", "-health-check"]` + D-10a poll on State.Health.Status, or (b) NO Docker HEALTHCHECK (or proxy `CMD ["/tempo", "-version"]`) + D-10a poll on State.Running == true PLUS an extra in-network curl to `/ready` before firing the synthetic push.

1. Deliver BACK-01 (Tempo monolithic against `tempo-traces`), BACK-03 (dual-knob retention semantics), and BACK-05 (OTLP receivers on internal-only `:14317`/`:14318`).

    Tempo's retention is a **two-phase mark-then-delete** lifecycle, and
    the two phases require two separate knobs:

      considered "old."
    - `tempo_compacted_block_retention: 1h` (default 1h) -- how long a
      compacted (already-merged) block sticks around before deletion.

    forever. See PITFALLS.md Pitfall 10. The role defaults set both
    knobs; the role template inlines the Pitfall 10 reference in a
    comment so the trap is visible.

    ## Healthcheck

    Tempo 2.10.5 is built on the `gcr.io/distroless/static-debian12` base
    -- no shell, no curl, no wget. Two possible Docker HEALTHCHECK shapes
    depending on whether the native `-health` binary flag is present in
    this tag:

    1. **If `/tempo -health` (or `-health-check`) exists in the image:**
       Docker HEALTHCHECK uses `CMD ["/tempo", "-health"]` (or the matching
       flag). The role's verify task polls `State.Health.Status` via
       `docker_container_info` until `healthy`.

    2. **If the native -health binary is NOT present in 2.10.5:** the
       Docker HEALTHCHECK is omitted (or set to a binary-alive proxy
       `CMD ["/tempo", "-version"]`), and OPS-06 compliance is achieved
       via the verify task's Ansible-side D-10a poll on `State.Running`
       PLUS an in-network curl to `http://tempo:3200/ready` before firing
       the synthetic push. PITFALLS Pitfall B context.

    Task 2 of the deploy plan probes the image at execute time
    (`docker run --rm grafana/tempo:2.10.5 -help 2>&1 | grep -i health`)
    and writes the role with whichever shape applies. The role default
    `tempo_healthcheck_enabled: true` is tuned by the probe outcome.
