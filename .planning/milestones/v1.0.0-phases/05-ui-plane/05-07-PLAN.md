The corrected block (what this plan produces):

```yaml
  - name: Loki
    type: loki
    uid: loki
    url: {{ grafana_loki_url }}
    access: proxy
    editable: false
    # D-79 + UAT gap 3 fix (05-07): trace_id derivedField wired for TWO sources:
    # 1. structured_metadata -- the canonical OTel-native path per D-78. Loki 3.x
    #    OTLP-native ingestion stores trace_id (+ span_id, trace_flags) as
    #    structured metadata on records pushed by OTel-instrumented apps.
    # 2. regex fallback -- extracts trace_id from log line BODY content for
    #    uninstrumented apps that hand-format `trace_id=<hex>` or `traceID=<hex>`
    #    in their stdout/stderr. Belt-and-suspenders.
    # Both fire independently; whichever matches first produces a clickable link.
    jsonData:
      derivedFields:
        - name: trace_id
          matcherType: structured_metadata
          matcherRegex: trace_id
          url: '${__value.raw}'
          datasourceUid: tempo
          urlDisplayLabel: 'View in Tempo'
        - name: trace_id_body
          matcherType: regex
          matcherRegex: '(?:trace_id|traceID)[=:]"?([a-f0-9]+)'
          url: '${__value.raw}'
          datasourceUid: tempo
          urlDisplayLabel: 'View in Tempo (from body)'
```

Notes on the regex:
- `(?:trace_id|traceID)` -- either snake_case or camelCase variant; covers
  both Go-conventional and JS/Java-conventional logging.
- `[=:]` -- separator: equals (e.g. `trace_id=abc123`) or colon (e.g.
  `traceID:abc123`).
- `"?` -- optional opening quote.
- `([a-f0-9]+)` -- captured trace_id is hex digits. OTel trace IDs are 32 hex
  chars; this regex is permissive (accepts any length >=1) to handle Jaeger-style
  IDs too.
- Match is single-line; Loki applies derived fields per log line.

Two derivedFields with different `name:` keys is the canonical multi-matcher
Grafana pattern (Grafana docs: "Multiple derived fields can be configured.
Each gets its own clickable link").

Naming the second one `trace_id_body` (not `trace_id`) avoids Grafana
deduplicating them as the same field -- having two distinct fields surfaces
two links in the log detail panel, which is fine UX for a debug/correlation
flow.

```markdown
### Trace-to-logs correlation

Telemetron wires bidirectional trace-to-logs correlation in Grafana:

**Tempo -> Loki** (`tracesToLogsV2` on the Tempo datasource):
- Customquery: `{${__tags}} | trace_id="${__span.traceId}"`
- Tag forwarded: `service.name` -> `service_name` (D-80; minimal one-tag default).
- Effect: clicking a span in Tempo Explore opens Loki Explore with logs
  filtered to the same service AND the same trace_id.

**Loki -> Tempo** (`derivedFields` on the Loki datasource):

Two matchers fire independently per log line. Whichever produces a hit shows
a clickable "View in Tempo" button in the log detail panel.

1. **Structured-metadata matcher (canonical, OTel-native)** -- matches log lines
   pushed via OTLP where the OTel SDK has attached `trace_id` as a structured-
   metadata field. This is the D-78 design contract: instrumented apps get
   reliable trace correlation. Loki 3.x stores OTel trace_id as structured
   metadata by default (not as a label, avoiding cardinality explosion).
2. **Regex matcher (fallback, body-embedded)** -- matches when the log line
   body contains text like `trace_id=abc123def` or `traceID:abc123def`.
   Pattern: `(?:trace_id|traceID)[=:]"?([a-f0-9]+)`. Useful for legacy apps
   or hand-rolled instrumentation that embeds the id in the log body
   rather than as a structured field.

#### Label mapping note (D-81 / 999.4 backlog)

Live Loki labels in telemetron are `{env, host, job, service_name}` -- the
OTel resource attribute `service.name` surfaces as `service_name` (OTel
convention) rather than `service` (Phase 3 D-47 spec). Phase 5 accepts this
per D-81 -- a future milestone may relabel via OTel exporter (option (c) in
999.4) to reconcile. Until then, all Grafana queries use `service_name` as
the canonical service identifier.

#### What this does NOT cover (M1 scope honesty)

E2E verification of the click-through requires:
- Either an OTel-instrumented app pushing traces+logs to telemetron's
  OTel Collector on `:4318` (OTLP HTTP) or `:4317` (OTLP gRPC), with both
  carrying the same trace_id;
- Or an uninstrumented app whose log lines contain `trace_id=<hex>` strings
  AND whose traces are independently pushed to Tempo (typical of homegrown
  Go services using a logging convention without full OTel SDK adoption).

Telemetron M1 ships no instrumented sample app. Operators verify the
click-through by deploying their own instrumented service against the stack.
The static wiring (derivedFields config -> Tempo datasourceUid linkage) is
verified at deploy time by Gate 9 D-73 Step 9 (`UI-04 -- assert Loki
datasource derivedFields trace_id is wired`).
```

Per Grafana 11 docs for Loki datasource derivedFields
(https://grafana.com/docs/grafana/latest/datasources/loki/configure-loki-data-source/#derived-fields):

> matcherType: Selects what kind of label to match against:
>   - label: Match against a stream label (indexed label).
>   - structured_metadata: Match against a structured-metadata field (the
>     OTel-native ingestion path stores trace_id, span_id, trace_flags as
>     structured metadata in Loki 3.x).
>   - regex (or leave matcherType absent): Match against a regex applied
>     to the log line body. The matcherRegex's first capture group is the
>     extracted value.

Grafana 13.0.1 (telemetron's pinned version per UI-01) supports all three.
</grafana_docs_reference>
