Live UAT on leviathan surfaced that `roles/karma/defaults/main.yml` line 59
defines:

```yaml
karma_healthcheck_test: ["CMD-SHELL", "wget --spider -q http://localhost:8080/health || exit 1"]
```

But `ghcr.io/prymitive/karma:v0.130` is built `FROM scratch` -- it ships ONLY
the `/karma` binary, plus /etc/ssl certificates. No `/bin/sh`, no `wget`, no
`curl`. The `CMD-SHELL` healthcheck form requires the shell to exist inside
the container, so docker runs `OCI runtime exec failed: exec: "/bin/sh":
stat /bin/sh: no such file or directory` every healthcheck interval (15s)
and the container goes `unhealthy` after 5 failures.

UAT confirms karma is FUNCTIONALLY HEALTHY:
- `GET /health` returns 200 "Pong"
- `POST /alerts.json` returns the registered telemetron alertmanager
- the in-network verify.yml curl-probe (line 27) PASSES against the karma container directly (when actually exercised)
- Karma UI loads at `http://leviathan:8082`

The only failure mode is the Docker-level HEALTHCHECK status (which then
makes the `Wait for karma container HEALTHCHECK to report healthy` task in
verify.yml hang and ultimately fail).

The standard Telemetron pattern for distroless/scratch images that lack
shell binaries is documented in STATE.md:
- Tempo: "Conditional Docker HEALTHCHECK pattern via tempo_healthcheck_enabled
  + Ansible omit magic value"
- Mimir: "Mimir image probe confirmed Outcome B: no native -health flag in
  grafana/mimir:3.0.6; default mimir_healthcheck_test=[CMD,/bin/mimir,-version]
  binary-alive proxy"

Karma's image has even less than Tempo/Mimir -- the `/karma` binary doesn't
have a `-version` or `--check-config` subcommand that returns 0 unambiguously
without side effects. The cleanest disposition (option (a) in the UAT gap brief)
is to flip the enable knob to `false` by default.

This isn't a regression in functionality. Karma WORKS. The healthcheck IS the
problem -- so the fix is to stop pretending we can run one inside a scratch image.

**Second-order discovery (revision iteration 1, surfaced by checker):**
Flipping `karma_healthcheck_enabled: false` makes the Wait-for-healthy task
SKIP cleanly -- but execution then proceeds directly into the 3 in-network

`cleanup` removes the container after run when `auto_remove` is false; the
combination `auto_remove: false` + `cleanup: true` + `detach: false` is
explicitly valid and is the documented escape hatch from the auto_remove
race.

```yaml
  community.docker.docker_container:
```

```yaml
    entrypoint: ["/bin/sh", "-c"]
    command:
      - >-
        curl -fsS http://{{ karma_container_name }}:{{ karma_container_port }}/health
        && echo "karma_health_ok"
  changed_when: false
  tags:
    - karma
    - karma-verify
```

Why `auto_remove: false` + `cleanup: true` + `detach: false`, and NOT the
grafana-style `docker_container_exec`:

- `docker_container_exec` requires the TARGET container (karma in this case)
  to have `/bin/sh` available for exec. Karma is FROM scratch -- no shell --
  so exec would fail immediately. This is the asymmetry from grafana
  (grafana-oss has /bin/sh + curl baked in).
- `auto_remove: true` + `detach: false` is documented invalid in
  community.docker (see ansible/ansible#45272). Once auto-remove fires, the
  container is gone before ansible reads stdout/exit status -- hence the
  `Cannot retrieve result as auto_remove is enabled` error.
- The standard escape hatch (documented in community.docker.docker_container
  module reference) is to set `auto_remove: false` and rely on `cleanup: true`
  for post-run removal -- ansible reads the result first, then cleanup
  removes the container. Idempotent across re-runs because `recreate: true`
  is also set.
- Same shape as the `karma_curl_image` one-shot container pattern that already
  exists in alertmanager (working in production since 04-02). The
  alertmanager verify.yml uses docker_container_exec only against AM itself
  (which has /bin/sh); for its CROSS-ROLE probes that need to reach via the
  bridge, it uses the same one-shot pattern with cleanup. We follow that
  convention here.
